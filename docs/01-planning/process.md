# Процесс команды

## Цель и исходные данные
Документ фиксирует методологию, доску, WIP-лимиты, Definition of Ready и Definition of Done. Команда состоит из двух участников; объём и технические риски могут уточняться по мере реализации.

## Выбранная методология: Scrumban
Scrumban сочетает визуальный поток Kanban с лёгким регулярным планированием. Он подходит команде из двух человек, потому что участники могут работать асинхронно, задачи берутся по мере освобождения WIP, а еженедельная проверка плана сохраняет связь с дедлайнами лабораторных. История перемещений задач станет основой метрик ЛР4.

## Доска задач
Колонки:
1. **Backlog** — идеи и истории, ещё не готовые к работе.
2. **Ready** — истории, прошедшие DoR, оценённые и имеющие критерии приёмки.
3. **In Progress** — разработка/тестирование истории.
4. **Review** — pull request открыт, авторские проверки пройдены, требуется проверка партнёра.
5. **Done** — критерии приёмки выполнены, ревью завершено, изменения объединены в основную ветку.

### Как настроить доску в трекере

1. Создать проект `Электронная библиотека кафедры` в GitHub Projects или GitLab Boards.
2. Настроить статусы/колонки: `Backlog`, `Ready`, `In Progress`, `Review`, `Done`.
3. Настроить поля `Story Points` (число), `WSJF` (число), `Release` (значения `MVP` / `Позже`), `Assignees` (ответственный участник) и `Iteration` (спринт). Использовать поле `Status` для отображения этапа выполнения задачи.
4. Создать 17 issues из `data/issues.csv` (для GitHub есть помощник `scripts/create_github_issues.py`; для GitLab CSV можно использовать как источник для ручного создания/импорта).
5. Связать задачи с репозиторием и соответствующими pull request. При первоначальной настройке помещать истории в Backlog; после проверки Definition of Ready переводить их в Ready. Для уже заполненной доски проверить, что все задачи в Ready действительно имеют критерии приёмки, оценки и понятные зависимости.
6. Зафиксировать лимиты `In Progress ≤ 2`, `Review ≤ 1`, активный WIP ≤ 3 в описании доски. Если трекер не поддерживает жёсткие WIP-лимиты, проверять их при каждом перемещении карточки.
7. Добавить ссылку на доску в `README.md` после создания проекта.

### WIP-лимиты и закон Литтла
| Колонка | WIP-лимит | Обоснование |
|---|---:|---|
| Ready | без жёсткого лимита, приоритеты пересматриваются еженедельно | Очередь готовых задач не должна заставлять брать работу без свободной ёмкости |
| In Progress | 2 | Не больше одной основной активной истории на участника |
| Review | 1 | Сначала завершается ревью уже начатой работы, а не накапливаются новые PR |
| Активный WIP суммарно | 3 | Сумма In Progress + Review |

Закон Литтла: `L = λ × W`, где `L` — средний WIP, `λ` — пропускная способность, `W` — среднее время прохождения задачи.

В условной истории пропускная способность составляет `(1+2+3+4+2+3+1+4)/8 = 2,5 истории в неделю`. Для предварительной иллюстрации предположим, что средний активный WIP равен 3 задачам. Тогда ожидаемое время прохождения `W = L/λ = 3/2,5 = 1,2 недели`.

Это расчётная гипотеза, а не измеренный факт: значения пропускной способности синтетические, а WIP-лимит 3 задаёт верхнюю границу, но не средний WIP. Если при той же средней загрузке пропускная способность упадёт до 2 историй в неделю, расчётное время прохождения вырастет до `3/2 = 1,5 недели`.

После 3–4 недель работы необходимо заменить условные значения фактическими данными команды, рассчитать средний WIP и пропускную способность и повторить оценку. Лимиты пересматриваются по результатам наблюдений.

Если трекер не поддерживает жёсткое техническое ограничение WIP, лимит фиксируется в описании доски и контролируется вручную.

## Definition of Ready (DoR)
История может перейти в Ready, если:
- сформулирована как «Как …, я хочу …, чтобы …»;
- есть не менее двух проверяемых критериев в формате Дано / Когда / Тогда;
- понятны пользовательская ценность и приоритет;
- оценка согласована обоими участниками;
- зависимости выявлены и задокументированы; блокирующие предпосылки выполнены либо явно запланированы раньше зависимой истории;
- размер не превышает 5 SP; более крупная история разбита;
- понятно, как проверить результат и какие тестовые данные нужны.

## Definition of Done (DoD)
История считается завершённой, если:
- реализация соответствует всем критериям приёмки;
- добавлены или обновлены автоматизированные тесты;
- тесты проходят локально; после настройки CI в ЛР2 также должен быть зелёный конвейер;
- код прошёл ревью второго участника;
- API/OpenAPI и README обновлены, если изменился контракт или запуск;
- секреты и реальные персональные данные не добавлены в репозиторий;
- изменения объединены через pull request в основную ветку;
- задача связана с PR и перемещена в Done;
- приложение и схема данных воспроизводимы на чистом окружении.

## Правила потока
- Новая задача берётся из Ready только при наличии свободного WIP.
- Если Review заполнен, команда сначала помогает завершить ревью.
- Блокировка отмечается в issue и обсуждается на ближайшей синхронизации; критическая блокировка сообщается сразу.
- История не переводится в Done только потому, что код написан: нужны приёмочные проверки и ревью.
- Движение карточки фиксируется в момент фактической смены состояния — это необходимо для достоверных метрик ЛР4.

## Вывод
Scrumban даёт лёгкий процесс для небольшой команды и создаёт данные для анализа потока. WIP-лимиты 2/1 ограничивают параллельную работу и делают ревью видимым узким местом.
