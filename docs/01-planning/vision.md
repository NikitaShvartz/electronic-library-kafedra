# Видение продукта

## Цель документа
Зафиксировать проблему, целевых пользователей, ценность и границы MVP электронной библиотеки кафедры.

## Исходные данные
Тема проекта выбрана из списка общего задания. Предполагается локальный сервис одной кафедры, небольшой книжный фонд и одна роль библиотекаря. Тема считается доступной по предоставленному списку занятых тем; перед финальной сдачей это нужно подтвердить у преподавателя.

## Проблема
Сведения о книгах и их доступности могут храниться в разрозненных таблицах или бумажных журналах. Библиотекарю трудно быстро проверить наличие экземпляра, записать выдачу и возврат, а студенту — найти книгу по названию или автору. Ручной учёт повышает риск двойной выдачи и потери информации.

## Целевые пользователи

| Роль | Основная потребность |
|---|---|
| Студент | Найти книгу и проверить доступность |
| Библиотекарь | Управлять каталогом и выдачами |
| Заведующий кафедрой | В будущем видеть статистику фонда |

1. **Студент** — ищет книгу, смотрит сведения и доступность экземпляров.
2. **Библиотекарь** — поддерживает каталог, оформляет выдачу и возврат, контролирует активные выдачи и очередь ожидания.
3. **Заведующий кафедрой** — потенциальный пользователь будущих отчётов; расширенная аналитика не входит в MVP.

## Ход проектирования
Сформированы роли, сценарии и измеримые критерии успеха; после этого граница MVP ограничена десятью историями, а расширенные отчёты и внешние интеграции вынесены за рамки первой поставки.

## Ценностное предложение
Единый каталог и простой REST API с интерфейсом Swagger позволяют быстро находить книги и вести базовый учёт движения экземпляров. Сервис предотвращает выдачу при нулевом остатке и хранит состояние активных/закрытых выдач.

## Ключевые сценарии
1. Студент открывает каталог, ищет книгу по названию или автору и смотрит доступность.
2. Авторизованный библиотекарь добавляет книгу и количество экземпляров.
3. Библиотекарь оформляет выдачу; сервис проверяет доступность и создаёт запись.
4. При возврате библиотекарь закрывает выдачу; доступное количество пересчитывается.
5. Библиотекарь просматривает активные выдачи и добавляет читателя в очередь ожидания, если книга недоступна.

## Критерии успеха
1. **Корректность поиска:** не менее 95% запросов из согласованного тестового набора возвращают ожидаемые книги.
2. **Целостность учёта:** 100% приёмочных сценариев выдачи/возврата проходят без отрицательного остатка и двойного закрытия выдачи.
3. **Производительность:** p95 ответа каталога/поиска не более 500 мс на тестовом наборе из 1 000 книг и до 10 одновременных клиентов. Это целевой порог для измерения в ЛР3, а не заявленный достигнутый результат.

## Границы MVP
В MVP входят 10 историй: просмотр каталога, поиск, карточка книги, авторизация библиотекаря, добавление книги, проверка доступности, выдача, возврат, список активных выдач и очередь ожидания.

**Не входит в MVP:** личные кабинеты студентов, автоматические email/SMS-уведомления, интеграция с внешними библиотечными каталогами/ISBN, электронная доставка файлов книг, межфилиальный учёт, расширенная аналитика, RFID/QR и промышленная интеграция с единой системой входа.

Для учебного прототипа предусмотрена одна роль «библиотекарь» и тестовый набор данных. Секреты не хранятся в репозитории. Публичный промышленный запуск не является целью этой лабораторной.

## Предполагаемый стек
- Python 3.11+ и FastAPI;
- SQLite для локального MVP, возможность перейти на PostgreSQL обсуждается после проверки требований;
- Swagger/OpenAPI как первый интерфейс пользователя;
- pytest для тестов;
- GitHub или GitLab для репозитория, issues, pull requests и доски.

## Вывод
Тема ограничена базовыми сценариями библиотечного учёта и подходит для MVP из 6–10 историй. Основные риски — корректность остатков и зависимость операций записи от авторизации; они отражены в бэклоге и приоритизации.
