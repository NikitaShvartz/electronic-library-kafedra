# Стратегия ветвления и правила ревью

Для «Электронной библиотеки» используем GitHub Flow. В `main` хранится рабочая версия приложения. Каждое изменение проходит через отдельную ветку и pull request.

## Ветки и коммиты

- Создаём ветку от актуальной `main` под одну задачу. Используем имена `feat/book-catalog`, `fix/empty-search`, `docs/branching` или `ci/composer-cache`.
- Стараемся завершать работу в ветке за 1–3 рабочих дня. Если задача не укладывается в этот срок или PR превышает 400 изменённых строк, делим работу на небольшие изменения. Сгенерированные файлы не входят в лимит строк.
- Для коммитов используем Conventional Commits в формате `<тип>: <описание>`. Примеры — `feat: add book catalog`, `fix: handle empty search`, `ci: cache Composer downloads`.

## Pull request и слияние

1. Автор берёт задачу на доске и переводит её в `In Progress`. В PR указывает ссылку на задачу и шаги проверки, затем переводит задачу в `Review`.
2. Партнёр проверяет изменения и оставляет хотя бы один содержательный комментарий. Автор отвечает в течение 24 часов и при необходимости вносит исправления. Документацию тоже проверяет партнёр.
3. Для слияния нужны одобрение партнёра и успешные обязательные проверки CI. Если после одобрения код изменился, партнёр повторно проверяет PR.
4. Сливаем PR через squash merge. Заголовок итогового коммита оформляем по Conventional Commits. После слияния удаляем рабочую ветку и переводим задачу в `Done`.

## Защита основной ветки

Когда в GitHub появится проверка CI, включаем для `main` обязательный pull request, минимум одно одобрение, сброс устаревших одобрений и обязательную успешную проверку CI. Прямые изменения `main` запрещены. Ответственных за ревью указываем в `.github/CODEOWNERS`.
